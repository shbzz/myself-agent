# 后端多 Agent 编排增量

本增量面向“Agent 编排创新应用”主线，**只增加后端能力，不修改前端**。
通过已有 `/next/api` 同源/登录边界提供配置和运行 API；通用单 Agent 会话继续可用。
这是平台核心的可运行增量，不代表知识库、人工介入/恢复、评测及比赛材料已全部完成。

## 1. 定义与运行快照

- Agent：角色（planner / worker / verifier）、声明技能、模型配置 ID、工具子集、并发上限、启停和系统提示。
- Team：2–8 个不同成员，团队最多 1–4 个并发叶任务，每个 Agent 最多 1–2 个并发。
- Workflow：声明式有向无环依赖图及嵌套控制结构，不执行 Python 条件表达式，不将固定示例作为产品边界。
- 三类定义写入既有版本化配置表。运行提交时冻结团队、工作流、Agent 版本、每个 Agent 的模型/供应商版本以及会话策略。
- Agent 角色和模型是不同概念，多个角色可以用同一个模型，也可以引用不同模型配置。
  所有启用成员必须声明工具能力并支持本轮选择的思考档位；模型容量须适配冻结的上下文预算。
- 技能是管理员声明，不是已经测得的能力分数。禁用成员不参与模型解析或调度。
- 并发修改设置或 MCP 白名单时，成员仍使用父运行冻结的策略版本与外部工具快照，不将新版本号混入旧值。
- 凭据保留为服务器私有版本引用；公开运行快照递归脱敏，不回显凭据引用或 API key。
- 每次 API 运行必须同时包含执行和独立验证；不把单 Agent API 包装称为团队运行。

## 2. 工作流执行语义

`examples/orchestration.json` 是可供注册的示例，不会自动写入正式数据。
节点 ID 在各自 Flow 内唯一，依赖必须存在且无环；嵌套 Flow 拥有自己的节点作用域。

| kind | 语义 |
| --- | --- |
| agent | 根据技能/工具选择一个启用的非 verifier Agent，独立模型上下文执行任务，产生待验证交接 |
| verify | 选择独立 verifier，读取依赖和工作区，返回严格布尔 JSON；随后平台在新的只读容器执行冻结命令并绑定产物指纹 |
| condition | `source` 必须是显式依赖的验证/控制结果，只接受已确定的布尔结果，只展开 on_true / on_false 之一 |
| loop | 执行 body，until 必须指向 body 内的 verify；只有该验证通过且整个 body 的激活产出被验证覆盖才收敛 |
| subworkflow | 执行嵌套 body，携带外层依赖的交接、待验证产出及验证证据 |

顺序由 depends_on 表达；无依赖冲突的就绪叶任务可以并行。
控制结构由单一协调器展开，叶任务使用有界线程池；本增量不宣称全局最优流水线调度。

每个 Flow 最多 16 个节点，定义总数最多 48，最多 3 层嵌套；循环最多 4 次。
每次运行另外有 max_steps（默认 48、最多 96），复用/跳过节点也计入步数，不能靠嵌套绕过限制。
模型调用总预算、超时、上下文、网页请求和 MCP 操作预算仍由冻结的会话策略限制，多个 Agent/尝试共用，不能各自重置。

## 3. 可解释动态调度与资源约束

先检查依赖就绪、启停、角色、技能包含关系和工具范围。
就绪任务排序分数：priority + 下游节点数 + min(就绪等待秒数,20)/10。
候选 Agent 依次按当前负载、已分配次数、额外技能数、ID 排序，并遵守成员及团队容量上限。
每次实际分配记录候选、排除原因、负载、分配次数、任务分数与选中成员。
这是一套可解释的自定义规则策略，不是训练所得算法，也没有声称已经证明相对基线的收益。

**工作区写任务互斥，只读任务可以并行。** 本增量没有宣称两个会修改工作区的 Agent 可以无冲突并行。
运行中已启动的写任务完成后才发放新的读/写租约，避免验证时产物被另一任务改写。
不改变原有“同一服务数据根目录最多一个顶层运行”的约束；团队并发发生在这个运行内部。

## 4. 独立验证与证据覆盖

验证通过同时要求：

1. 独立 verifier 的最终 JSON 中 passed 是真正的布尔 true，不能是字符串；
2. 冻结的每条验证命令均实际执行，命令、退出码和输出可查，全部退出码为 0；
3. 模型工具容器已关闭，验证命令使用新的、无网络、工作区只读的容器；
4. 验证前后产物指纹相同；
5. 最终所有激活的 Agent 产出都被成功验证的依赖覆盖，且没有未处理的拒绝结果。

因此作者自报成功、verifier 自报成功、存在一个与其他产出无关的成功验证，都不能直接让运行成功。
未覆盖的输出通过 unverified_paths 暴露。旧的拒绝结果保留为任务记录；只有显式条件修复或循环收敛才能消解，不能被普通下游任务的完成抹掉。

验证器工具不允许直接文件写入或 MCP 业务调用；容器读写权限是独立硬约束，不依赖提示词。
普通只读任务也不能要求 mutating 工具。MCP 业务调用需写任务及会话授权，授权只能收窄，不能扩大。
当最终有效工具范围包含 MCP 发现或业务调用时，Agent 仅收到冻结已启用服务的 ID/名称目录，标明为配置资料；不传入私有端点、凭据或凭据引用。无 MCP 权限的角色不收到目录，只读节点不能因声明业务工具而扩大权限。建议需要业务调用的角色同时声明 mcp_list_tools，以发现白名单工具及参数，平台不会自动补权限。
验证输出是证据，不是对恶意用户代码的形式化证明。检查质量取决于验收定义：若命令运行可被作者改写的测试文件，测试本身也可能被修改；优先使用冻结的内联断言或外部受控验收资料，不能把可改测试自动当作可信基准。

产物清单通过目录文件描述符、不跟随链接的读取生成，最多 1000 项、单文件 16 MiB、累计 32 MiB、10 秒；拒绝链接/特殊文件，排除 .git 元数据。
容器使用既有固定摘要 Python 镜像、无网络、只读根文件系统、非 root 用户及资源限制；平台凭据不挂入容器。

## 5. 有界反馈与局部修复

verify.repair_targets 可指定其祖先节点，不能跨 Flow 指向任意任务。
验证拒绝后，loop 收集失败验证的修复目标，计算目标与下游依赖闭包，再次调度该范围；未受影响的已完成节点在本次循环内复用并保留原始产出来源。
未显式指定目标时，保守重跑 body 内执行节点及终止验证。反馈包含真实失败命令/输出与未覆盖产出，修复提示不是虚构的成功报告。
再次分配依据当时负载和分配记录重新选择成员，可能交给另一个合格 Agent。

循环达到上限仍未通过时保留拒绝结果，下游普通任务跳过，顶层运行失败；不会无限重试。
模型/工具异常（含无效 verifier JSON、预算耗尽）停止运行，**不自动重放**可能有副作用的操作。

## 6. API

以下以 `/next/api/orchestration` 为前缀，写请求沿用 JSON、同源及现有认证边界。

- POST /agents、/teams、/workflows：保存新版本，字段见数据模型及示例。
- GET /agents：发现最新 Agent；可用 skill、enabled 过滤。
- GET /teams、/workflows：列出最新定义。
- GET /{agents|teams|workflows}/{id}/versions：查看定义历史版本。
- POST /runs：创建运行，返回 202；提交字段如下。
- GET /runs?session_id=...：该会话的编排运行。
- GET /runs/{id}：父运行、脱敏快照、任务/尝试、结果/用量/证据。
- GET /runs/{id}/events?after=0：按事件序号分页（每页最多 200）；也可使用既有会话 SSE。
- POST /runs/{id}/cancel：停止对应进程组并清理该父运行标签下的容器，不影响无关容器。

```json
{
  "session_id": "现有会话的32位十六进制ID",
  "request_id": "新的32位十六进制幂等请求ID",
  "text": "本次自由提出的复杂任务及范围",
  "team_id": "example-team",
  "workflow_id": "example-flow",
  "reasoning_effort": "off"
}
```

示例中的 agents 逐个 POST、team POST、workflow POST 后才可运行；**POST /runs 会实际调用模型**。
可选的精确模型与思考等级由已有供应商/模型设置配置，示例没有内置凭据或固定提供商。
request_id 重试返回原运行/原快照，不重复派发；同一编号不同任务/团队/工作流返回 409。
提交父运行与快照使用同一 SQLite 事务，失败回滚，不能留下缺少定义的活动运行。

## 7. 持久状态、异常与当前边界

新增 orchestrations、orchestration_tasks 两张表；既有用户表与记录不删除、不覆盖。
任务状态包含 running / succeeded / rejected / reused / skipped / failed / interrupted / cancelled。
运行保留每个路径、Agent、尝试 ID、结果、验证、复用来源和调度/反馈事件。
取消后不能被迟到的成功或异常覆盖成成功；启动工作进程失败也会释放活动运行并记录脱敏错误类型。
服务重启会把未完成任务标记 interrupted 并清理带父运行标签的容器，**不会自动重放**外部写入。
本增量没有跨运行自动续跑、人工审批/继续节点、分布式任务队列、知识库/长期记忆或可视化编排界面，不能声称这些已经完成。
每个叶任务及修复尝试有独立上下文，只收到任务、依赖交接与有界反馈；目前不继承普通会话的完整模型检查点/图片历史。

## 8. 验证证据

必需检查：home 的 `competition/scripts/check-home.sh` 已通过：167 项 pytest、Ruff/格式、旧 JS 语法和 TypeScript/Vite；保留既有 LangGraph durability 警告。前端源码无差异，构建资源哈希保持不变。
确定性测试覆盖顺序/真正并行、写互斥、两种条件分支、嵌套、依赖覆盖、优先级/动态选择、有界局部修复、失败与预算、快照/幂等/事务、取消/重启、MCP 目录的四种有效权限组合与凭据不回显和真实 Docker。
测试中的脚本模型是明确的离线夹具，不充当自主模型成功的证据。

另一次隔离真实任务使用 DeepSeek Flash、thinking off，预算最多 14 次模型调用 / 180 秒。
已知缺陷初始项目先被独立验证拒绝，条件分支转入修复；调度器从用于只读分析的 builder-a 转选 builder-b，修复后验证成功。
实际 13 次调用、20.399 秒；输入 24662、输出 986、总计 25648 tokens，其中缓存输入 15488。
这是一次真实闭环的观察，不是成功率/提效结论；不将已知故障注入包装成模型自发犯错。

开发过程中按用户要求使用 WorkBuddy `cn:deepseek-v4.1-flash` / max 外部子代理生成合约边界测试，主代理复核后集成 25 项通过测试。
该开发辅助任务实际 5 次请求、97189 tokens（缓存输入 63616），不与平台实测用量混算，也不冒充产品的多 Agent 功能。
证据、模型记录、环境凭据、数据库及主机专用脚本全部保留在 Git 之外。正式部署不得复制验证团队、策略、夹具或测试数据。
